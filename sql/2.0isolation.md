### ① row_trx_id = 1000

row_trx_id >= max_trx_id (1003) → ❌ 不可见。
含义：这个事务是快照生成之后才创建出来的，快照看不到它的修改。

初始：余额 = 100，行版本 `row_trx_id=999`（事务 999 早已提交）

- 开启事务 B，生成 ReadView：
当前系统活跃事务只有 A (trx_id=1001)
m_ids={1001}, min=1001, max=1002
- 事务 B 去读最新行：余额 = 200，`row_trx_id=1001`
判断：1001 在 m_ids 集合 → ❌ 不可见
→ 沿着 roll_pointer 跳到 undo 旧版本，余额 = 100，`row_trx_id=999`
判断：999 <min_trx_id (1001) → ✅ 可见，返回 100。
> 这就是为什么 B 读到 100。

# RR）
ReadView 三个核心值（一旦生成永久固定）

- `m_ids`：快照瞬间，所有活跃未提交事务 ID 集合
- `min_trx_id`：`m_ids` 里面最小事务 ID
- `max_trx_id`：快照生成那一刻，**下一个将要分配的事务 ID**

一行数据，每生成一个新版本，新版本就会把自己行上 trx_id 改成当前事务的 trx_id。旧版本（undo 里）保留它当时的 trx_id 记为row_trx_id。
可见性判断顺序：

1. `row_trx_id < min_trx_id` → ✅ **可见**（快照前就提交的事务修改）
2. `row_trx_id >= max_trx_id` → ❌ **不可见**（快照创建之后才新开的事务，无论提交与否，一律看不见）
3. `min_trx_id ≤ row_trx_id < max_trx_id`
   - 如果 `row_trx_id` 在 `m_ids` → ❌ 不可见（快照创建时该事务还活着没提交）
   - 如果 `row_trx_id` **不在 m_ids** → ✅ 可见（快照创建前，该事务已经提交完毕）

> 重点：RR 中，**只要事务是快照之后才创建的（trx_id ≥ max_trx_id），哪怕它提交了，依旧不可见**。
----------------------------------------------
RR: 只能看到 快照生成时 已经提交的数据
----------------------------------------------
##  RR 经典演示案例（B 看不到 A 修改）

1. T0：B begin;
2. T1：B 执行第一条 select → **生成 ReadView（快照冻结）**
3. T2：A 开启事务，修改余额 = 200，commit
4. T3：B 再次 select，复用老的 ReadView
👉 A 的 trx_id 在 ReadView 创建之后才产生，B 判断不可见，读到旧 100
---------------------
##  RR 经典演示案例（B 看到 A 修改）

1. T0：B begin; 事务标记为开启，分配事务 ID（如果后面写操作才分配，只读事务甚至延迟分配 trx_id），**没有 ReadView**
2. T1：A 事务：修改余额→commit，A (trx_id=1001)，执行完毕，事务结束。A 已经不在活跃事务列表
3. T2：B 执行第一条 select，**生成 ReadView**
ReadView 采集当前全局活跃事务：A 已经提交，不在 m_ids；
可见性判断：行版本 trx_id=1001，小于 max_trx_id，并且这个事务已经提交 → **B 可以读到 200**
----------------------------------------------
RR回溯: 沿着 undo 版本链向前回溯，找到第一个满足 ReadView 可见规则的旧版本，作为查询结果。

# 长事务内存问题
- T0：开启长事务 B，执行第一条 select，生成 ReadView（快照 S，时间点很早），然后 B 卡住，很久不提交。
- T1、T2、T3…… 大量其他事务不断更新同表不同行，每次更新都会生成 undo 旧版本。
- 这些新产生的 undo 版本，**版本的 trx_id 都大于快照 S 的 max_trx_id**。
意味着：长事务 B 如果后面去读这些行，需要沿着 undo 链回溯读到旧版本。
→ purge 线程**不敢删除这些 undo**，万一 B 突然查询，就找不到历史版本了。
- 于是 undo 日志持续堆积，占用磁盘（不是内存！undo 是落盘的，存在 ibdata/undo 独立表空间）。

伪清理
当**所有持有早于该 undo 版本快照的事务全部提交结束**，没有任何 ReadView 还需要这个 undo 版本，purge 线程才会后台清理这个 undo 记录。
清理只是标记空间可复用；**旧 ibdata 文件不会缩小，只是内部空间标记空闲，可以后续继续写 undo**。
----------------------------------------------
> **同一个事务，同一行多次修改，只存【修改前原始镜像】，中间迭代值不保存在 undo 版本链。**
## 对比另一种情况：多次修改，每一次都 commit

事务 A：改 100→150 commit
事务 B：改 150→180 commit
事务 C：改 180→220 commit
事务 D：改 220→260 commit
事务 E：改 260→300 commit
👉 这时**会产生 5 个 undo 节点**，版本链 5 段，因为每次都是独立事务提交，每一次修改都要对外可见，需要保留历史版本给 MVCC
----------------------------------------------
BEGIN;
SELECT count(*) FROM order; -- 时间点T1快照
-- 此时别的线程插入了一条订单并提交
SELECT count(*) FROM order; -- 依然读到T1的数据，看不到新订单
COMMIT;

**事务会持续持有一个事务视图（MVCC 的 read view）**
- 从 `begin` 那一刻就创建 read view，直到 `commit` 才销毁。
- 在这个事务持续期间，InnoDB **不能清理 undo log**。
- 如果这个只读事务长时间不提交，undo 堆积、历史版本保留，会导致：磁盘膨胀、行版本过多、查询变慢。
----------------------------------------------
innodb_undo_tablespaces: **把 undo log（回滚段）从 ibdata1 系统表空间剥离，拆成多个独立 undo 表空间文件**，典型设成 2
    5.5 及更早：所有 undo 日志全部塞在 `ibdata1`（系统表空间）里面。
    ibdata1 有一个致命问题：**文件只会涨，不会自动收缩**。
    一旦出现大事务 / 长事务，undo 疯狂堆积，ibdata1 膨胀到几十 GB，**就算事务提交、purge 清理完 undo，
    ibdata1 文件大小也不会变小**。想回收磁盘空间只能全库导出、重建实例，线上非常痛苦。

MySQL 5.6 或者更新版本，把 innodb_undo_tablespaces 设置成 2（或更大的值）。如果真的出现大事务导致回滚段过大，这样设置后清理起来更方便。

----------------------------------------------


当数据库上有多个事务同时执行的时候，就可能出现脏读（dirty read）、不可重复读（non-repeatable read）、
幻读（phantom read）的问题，为了解决这些问题，就有了“隔离级别”的概念。

SQL 标准的事务隔离级别包括：读未提交（read uncommitted）、读提交（read committed）、
可重复读（repeatable read）和串行化（serializable ）
