`--single-transaction` 靠**InnoDB 的 MVCC + 一致性视图**做热备份，**只对支持事务的 InnoDB 生效**；
FTWRL（`FLUSH TABLES WITH READ LOCK`）是**全引擎通用的锁方案**，专门用来处理 MyISAM 这类不支持事务的表，代价是**整库只读锁，阻塞所有写入**。

---------------------------------------------
备份开始前，执行 START TRANSACTION; 开启事务，拿到一个一致性快照（视图）
1.在开启瞬间生成一个 read view：里面记录当前活跃事务 ID。全局生效 即全局均参考这一个read view

mysqldump 只是保存建立视图的那个点处的所有已提交的数据行，它并不会保存或者说更新之后的提交的新数据
mysqldump 建立一致性读视图后，读取的是“这个 Read View 所允许看到的数据版本”，从而得到一个一致的快照。
备份期间后来提交的新修改，不会出现在这次备份的数据里。

如果你想把 T1 之后发生的 Charlie、David、Eve 也纳入恢复体系，那就不是靠这一次 mysqldump 解决，而通常需要结合 binlog
mysqldump = 某个一致性快照
binlog = 快照之后发生的变化

---------------------------------------------
MDL（metadata lock) 表级锁 系统默认会加

当对一个表做增删改查操作的时候，加 MDL 读锁；当要对表做结构变更操作的时候，加 MDL 写锁

读锁之间不互斥，因此可以有多个线程同时对一张表增删改查。
读写锁之间、写锁之间是互斥的，用来保证变更表结构操作的安全性。因此，如果有两个线程要同时给一个表加字段， 其中一个要等另一个执行完才能开始执行。
---------------------------------------------

给一个小表加个字段，导致整个库挂了:
    事务A/B 对表t 进行select查询操作 但都是长事务 即不立即结束 即一直占用MDL读锁
    此时C事务 alter该表 会尝试使用MDL写锁 则阻塞等待A/B释放读锁
    此时业务侧大爆发 产生很多事务读操作 则均阻塞 直至崩溃

解决方案:
    1.如果你要做 DDL 变更的表刚好有长事务在执行，要考虑先暂停 DDL，或者 kill 掉这个长事务
    在 MySQL 的 information_schema 库的 innodb_trx 表中，你可以查到当前执行中的事务
    2.在 alter table 语句里面设定等待时间，如果在这个指定的等待时间里面能够拿到 MDL 写锁最好，
    拿不到也不要阻塞后面的业务语句，先放弃

---------------------------------------------
如果备份是在备库上执行，备份过程中主库执行了 DDL，备库最终会把这个 DDL 通过 binlog/复制执行掉。
由于 --single-transaction 只对事务性 DML 提供一致性快照，而 DDL 不是这种一致性读可以“冻结”的对象，
所以可能出现同一次 mysqldump 中，不同表/不同阶段看到的 schema 不一致。

假设 mysqldump 已经开始：
T1 t表：

id | name
---+------
1  | Alice
2  | Bob

Read View 建立。

然后主库： ALTER TABLE t ADD COLUMN age INT;

复制到备库。

备库变成：

t：

id | name | age
---+------+----
1  | Alice| NULL
2  | Bob  | NULL

但是 mysqldump 的 Read View 仍然是 T1。


MySQL 对 --single-transaction 有一个非常重要的限制 --single-transaction 的一致性主要针对：
InnoDB 表的数据。 它并不能阻止其他事务执行：
ALTER TABLE
DROP TABLE
CREATE TABLE
TRUNCATE TABLE
尤其是 DDL。 所以官方通常会强调： 使用 --single-transaction 时，不应该在备份期间执行 DDL

MVCC 能保证： 数据的一致性 但是 MVCC 不保证： schema 的一致性
MVCC 能冻结“数据版本”，但不能冻结“表结构”。
