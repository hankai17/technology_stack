MySQL 数据恢复机制讨论总结
一、线程与行锁：max_connections/引擎线程名额的死锁
InnoDB 有"同时进入引擎执行的线程数"上限（默认 128），管的是 CPU 计算资源，与锁、与行无关。
死锁场景：线程 1 持有 id=1 的行锁后空闲（不占名额）；128 个线程因等这行锁阻塞。若等锁线程也算进 128 名额，名额被占满，线程 1 想提交却进不了引擎，形成"互相等"的死锁。
结论：等锁线程不计入执行名额，避免系统堵死。
关键区分： 名额管"能同时跑的计算线程"，行锁管"能同时改同一行的事务"，是两套正交资源。

二、为什么需要 binlog_format=row
statement 记 SQL 语句、从库重算——遇到不确定函数（now/rand/uuid）、并发时序、非唯一条件更新等，主从会不一致。
row 记"行改成了什么"，从库照抄，天然一致，且是 CDC 工具（Canal/Debezium）解析前提。
代价：row 格式 binlog 体积更大。
三、闪回（binlog 反向撤销）中的 event 翻转
撤销一次 insert：把原始的 Write_rows 事件改造成 Delete_rows（删掉当初插入的行）。
撤销一次 delete：反向，把 Delete_rows 改成 Write_rows（把删掉的旧值插回）。
核心：翻转 event 类型，构造"逆操作"。
四、备份体系：全量 + binlog（不是 redo log）
时间点恢复方案 = 全量备份 + binlog 增量重放。
redo log 不参与时间点恢复，它是崩溃恢复用的：环形、会被覆盖、只记物理页变化（无语句概念），无法筛选/长期保留。
五、redo log 在断电重启中的作用
作用：把"已提交但未刷盘的数据"重做回来，保证不丢数据。
机制：WAL 先写 redo 再算提交；重启时从 checkpoint 往后重放，有 commit 标记的 redo、无标记的 undo 回滚。
innodb_flush_log_at_trx_commit=1 保证提交即落盘。
六、数据页刷盘进度 ≠ 事务提交进度
一个数据页混着多个事务的修改；刷盘按页整页刷，不管事务是否提交。
所以 checkpoint 之后仍可能有：①已提交未刷盘（靠 redo 补）②未提交未刷盘（忽略）③未提交但已刷盘（靠 undo 撤）。
checkpoint 定义的是"页的新旧"，不保证"事务都提交"。
七、GTID 跳过误操作的原理
正确顺序：

先恢复全量备份到临时库（此时 gtid_executed = 备份点之前的 GTID）；
伪造 gtid1：set gtid_next=gtid1; begin; commit; ——空事务把误删的 gtid1 塞进 gtid_executed 集合；
从备份点往后回放 binlog：每遇事务先查集合，gtid1 命中则自动跳过（GTID"至多执行一次"天性），其余照常执行。
易错点澄清：

起点是"全量备份点"，不是"误操作点"；误删是被中途绕过去的。
伪造必须在全量恢复之后做（集合要先建起来）。
被跳过的仅 gtid1 一条，其前后数据照常应用。
gtid_next 是单值入口，gtid_executed 是集合落点；"1-100"那种看着像 MAX 的写法只是集合的区间压缩表示。
八、并行复制加速恢复
普通方式：读 binlog 文件，串行一条条重放，慢。
加速方式：把临时库设为线上备库的从库，用 change replication filter replicate_do_table=(表名) 只同步受害表，再 start slave，利用并行复制多线程追平。
快的本质是 串行→并行 + 只同步必要的表，不是"文件 IO 换内存拷贝"（两种方式都要读写，都要落盘）。
九、备库 binlog 文件缺失的原因
show binary logs 最小是 master.000007，但临时库需要从 master.000005 起 —— 说明 000005/000006 超过保留期被自动清理（expire_logs_days 等）。
不是"两库 binlog 内容不一致"，而是备库本地文件过期缺失。
解决：靠独立保存更久的 binlog 备份系统兜底，从那里找回缺失文件。
