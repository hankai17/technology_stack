MySQL 核心概念贯穿总结（存档）
一、主线：一条 SQL 的完整旅程
理解 MySQL 所有概念，最好的办法是先抓住一条主干，再把零散名词挂到对应位置。一条 SQL 从发出到返回，依次经过：

连接阶段：客户端 TCP 连入 → 分配一个服务线程 → 在该连接上建立会话（会话变量、默认库、权限等上下文都挂在这里）。
解析：SQL 文本 → 解析树 → 检查表/列/权限（此时可能拿元数据锁 MDL，拿不到就等）。
优化：选索引、定 join 顺序、生成执行计划。
执行：调用存储引擎，按计划取数。
引擎层取数：查 Buffer Pool → 不在就去磁盘读（IO 等待）→ 改数据要先拿行锁（锁等待）→ 提交时写 redo/undo、刷脏页（后台线程做）。
返回：结果集回给客户端。
关键认知：所有"等待"本质是同一件事——执行链走到某一步，被某个闸门挡住。它们不是并列的名词，而是一条流水线上分布在不同工位的阻塞点。下面每一节的问题，都能落回这条主干的某一步。

二、连接与会话：MySQL 的线程模型
默认「每连接一线程」：客户端每建一个连接，MySQL 分配一个专门的服务线程，由它独自处理该连接上的所有 SQL，直到断开。连接在，线程在；连接断，线程走。

会话即连接本身：MySQL 没有独立于连接的会话实体。事务、变量、临时表等会话状态都挂在连接上，连接一断会话即结束——这就是"会话由连接引发"的真正含义。

两类线程：

前台线程：每个连接一个，负责读包、解析、执行、回包。
后台线程：与连接无关、常驻，如监听/accept、InnoDB I/O 与 redo 线程、page cleaner、purge、复制 dump 线程等，数量由参数控制。
为什么不用事件驱动：事件驱动适合"大量连接、事件稀疏"；而 MySQL 每个连接一旦有活干往往是长阻塞查询，瓶颈在磁盘和锁，不在调度。让内核处理阻塞、每线程串行执行，模型最简单、隔离最干净；改成事件驱动需把整条同步执行栈改为状态机，代价极大。

线程池是可选项：Percona、企业版、MariaDB 提供线程池插件，用固定 worker + 事件分发处理海量连接，正是高并发优化方向，但社区版默认关闭。

本质：用"默认简单、向后兼容"换执行模型简单，把更高效的线程池做成可选插件，是明确的工程取舍，而非错误设计。

三、KILL 为什么会"杀不掉"
两种 KILL：

KILL QUERY：只终止当前语句，连接和会话保留。
KILL CONNECTION（等同 KILL）：终止整个连接，连线程一起清掉。
根因——等待点是否检查 kill 标记：

可被唤醒的条件等待（如 update 等行锁用 pthread_cond_timedwait）：被唤醒后检查状态，能感知 kill，能退出。
用户态自转的 sleep 循环（如等进入 InnoDB 资格的线程）：每 10ms 判断能否进入，不行就 nanosleep，循环体内不检查标记，即使状态已置为 KILL_QUERY 也感知不到，退不出来。
准确表述：能否响应 kill，取决于当前这段代码有没有定期检查 kill 标记，而不是以"是否进入 InnoDB"为界。信号一直在，不是"收不到"，而是"走到的这段代码不看它"。此外，等锁、等 IO、等 MDL、事务回滚等，也都是执行链上不同的阻塞点，响应快慢取决于该点是否在检查标记。

四、Ctrl+C 到底发生了什么
误解：以为 Ctrl+C 是客户端本地撤回请求。

真相：客户端另开一条连接，向服务端发 KILL QUERY。

网络交互中，客户端无法直接操作服务端线程；Ctrl+C 只是本地不再等，服务端线程该跑还在跑。
MySQL 用停等协议：同一条连接上，语句没返回前，再发命令递不进去。所以不能在原连接补"停止"命令。
客户端真正做法：新开连接发 KILL QUERY <线程id>，服务端设 kill 标记，再走上一节那套"看漂在哪段代码"的逻辑。
结论：Ctrl+C 完并非万事大吉，真正停止在服务端，要走一整套后端流程（另开连接、发命令、设标记、等检查点、可能回滚）。正常 Ctrl+C 是对自己查询的正当自我管理，不是攻击；KILL 需权限（PROCESS + SUPER 或 CONNECTION_ADMIN 等），无权限不能 kill 他人。

五、"表多导致连接慢"的真相
误解：表多 → 服务端建索引/元数据慢 → 连接慢。

真相：连接本身（TCP 握手、认证、取权限）与表数无关。慢的是客户端——默认开启的 Tab 自动补全，连上后主动做三件事：执行 show databases → 切库执行 show tables → 在本地把结果构建成哈希表（最耗时）。表越多，本地建哈希表越久，于是感觉"连接卡住"。

关键点：不是甩锅——耗时工作发生在客户端进程内存里，是客户端为补全功能自己追加的，不是服务端建索引。

解法：连接时加 -A（--no-auto-rehash）关闭自动补全，客户端秒连，代价是失去 Tab 补全。

六、如何把这些串起来（学习方法）
面对"不知道自己不知道什么"的困境，破法是先建主干地图，再填细节：

把 SQL 执行 6 步画成一条横线，每学一个新概念就标它落在哪一步；落不进去说明主干没吃透。
每遇"等待/卡住"，先问：卡在第几步？闸门是什么（锁/IO/MDL/回滚）？
概念永远在"顺序 + 因果"里才有意义；单独背记不住，放进流程位置里自然记住。
最有效实践：拿一条真实慢 SQL，用 SHOW PROCESSLIST 看 State 停在什么词，回到 6 步对号入座，看几次就长在脑子里。
七、贯穿全局的一句话
SQL 的一生是一条流水线（连接 → 解析 → 优化 → 执行 → 引擎取数 → 返回）；连接与会话是它的容器，各种"等待"是流水线上不同工位的闸门，KILL 是往闸门处投递的一个标记，能否生效取决于该工位查不查这个标记；而"连接慢""杀不掉"等表象，往往不是性能或命令本身的问题，而是工作发生在流水线的哪一段、哪个部件（客户端还是服务端）上被误判了。
