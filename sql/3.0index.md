以 InnoDB 的一个整数字段索引为例，这个 N 差不多是 1200。这棵树高是 4 的时候，就可以存 1200 的 3 次方个值，这已经 17 亿了。
考虑到树根的数据块总是在内存中的，一个 10 亿行的表上一个整数字段的索引，查找一个值最多只需要访问 3 次磁盘。
其实，树的第二层也有很大概率在内存中，那么访问磁盘的平均次数就更少了。

传统数据库：索引树叶子存磁盘地址，数据单独放一块堆。
InnoDB：**聚簇索引树(主键 B+ 树)叶子 = 全部数据；
其他索引(非主键 B+ 树)都是独立小树，叶子存主键当做逻辑指针，靠主键去聚簇树拿完整数据**
---------------------------------------------------
                    [非叶子页： 10, 页号P2 | 20, 页号P3]  ← 只有key+页号，没有name/age
                            ↙️              ↘️
            [非叶子页P2：5,P4 | 8,P5]        [非叶子页P3：15,P6 | 18,P7] ← 同样只有导航信息
                 ↙️         ↘️                    ↙️         ↘️
[叶子页P4]id=1,name=A,age=20    [叶子页P5]id=8,name=H,age=22 ← 叶子才有完整行
[叶子页P6]id=10,name=J,age=30   [叶子页P7]id=20,name=T,age=25

非叶子节点怎么描述子页的 key 范围: 非叶子页里存的条目格式：`(分割键 key, 子页号)` 重点：**这个分割键，代表「子页里面最大的 key」**（InnoDB B + 树的约定）

1. **非叶子节点：轻量化，尽可能多放索引条目，压低树高度，减少磁盘 IO。只需要 key + 页号做路由，不需要业务数据。**
2. **叶子节点：存放这棵索引对应的完整记录（聚簇索引是整行；二级索引是索引键 + 主键），是最终读取数据的地方。**

回表:
如果语句是 select * from T where ID=500，即主键查询方式，则只需要搜索 ID 这棵 B+ 树；
如果语句是 select * from T where k=5，即普通索引查询方式，则需要先搜索 k 索引树，得到 ID 的值为 500，再到 ID 索引树搜索一次。这个过程称为回表。
---------------------------------------------------
CREATE TABLE `tuser` (
`id` int(11) NOT NULL,
`id_card` varchar(32) DEFAULT NULL,
`name` varchar(32) DEFAULT NULL,
`age` int(11) DEFAULT NULL,
`ismale` tinyint(1) DEFAULT NULL,
PRIMARY KEY (`id`),
KEY `id_card` (`id_card`),
KEY `name_age` (`name`,`age`)
) ENGINE=InnoDB

1. `KEY id_card(id_card)`：索引键 = id_card；叶子存`(id_card,id)`；查 name 需要回表，索引体积小。
2. `KEY idx_idcard_name(id_card,name)`：索引键 =`(id_card,name)`；叶子存`(id_card,name,id)`；查 name 可以走覆盖索引不用回表；索引体积更大，写开销更高。

联合索引 (a,b) 只有一棵 B + 树；因为记录先按 a 排序，这一棵树可以当做 a 的单列索引来用。
也就是说，A、B 这种场景适合 A 单独查询，或者 A、B 同时查询，但单独查 B 是不行的。考虑到业务上 A 的查询比较热门，其次是 A、B 一起查询的场景也比较热门，但单独查 B 的场景很少。

索引下推
在 MySQL 5.6 之前，只能从 ID3 开始一个个回表。到主键索引上找出数据行，再对比字段值。
而 MySQL 5.6 引入的索引下推优化（index condition pushdown)， 可以在索引遍历过程中，对索引中包含的字段先做判断，直接过滤掉不满足条件的记录，减少回表次数。
---------------------------------------------------
KEY c(c)      c 相同的时候，再按主键(a,b)排序
KEY ca(c,a) c 相同，a 从小到大排
KEY cb(c,b) c 相同，b 从小到大排

c=N,a=1,b=9 
c=N,a=2,b=1 
c=N,a=3,b=5
KEY c(c) 索引 c 叶子里 a按顺序排是：1，2，3 b 的值是 9,1,5 → b 是乱序！

KEY c：按c排序，c 相同按主键(a,b)排。所以 a 有序，b 无序。
KEY ca(c,a)：按c,a排序。c 相同，a 有序。
KEY cb(c,b)：按c,b排序。c 相同，b 有序。
KEY ca 是冗余索引。 业务如果只有 where c=N order by a，不需要单独建 ca，KEY c就够用。
KEY cb 才有价值：为了 where c=N order by b limit 1，利用索引天然有序，省去内存排序。
