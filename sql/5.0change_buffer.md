插入一条数据时，索引页在不在 Buffer Pool，会导致什么不同。
一、先准备一张表
假设用户身份证号码在业务上必须唯一，我们建立两个结构相同、索引不同的表，方便对比。
CREATE TABLE user_unique (
    id BIGINT PRIMARY KEY,
    id_card VARCHAR(18),
    name VARCHAR(50),
    UNIQUE KEY uk_id_card (id_card)
) ENGINE=InnoDB;

CREATE TABLE user_normal (
    id BIGINT PRIMARY KEY,
    id_card VARCHAR(18),
    name VARCHAR(50),
    KEY idx_id_card (id_card)
) ENGINE=InnoDB;


为了方便理解，假设两张表中已经有很多数据，现在要插入：
INSERT INTO user_unique
VALUES (1001, '110101200001011234', '张三');

INSERT INTO user_normal
VALUES (1001, '110101200001011234', '张三');


这里假设两条记录都没有重复的 id_card，主键 id 也不存在冲突。
注意：我们讨论的是 id_card 对应的二级索引页，不是主键索引页。
二、情况 1：唯一索引页在 Buffer Pool 中
唯一索引：uk_id_card 的目标页已在内存

Buffer Pool
索引页中保存着相邻的身份证号码
……110101200001011233、110101200001011235……

插入 110101200001011234

1. 在内存索引页中检查是否已有相同的值。
2. 确认没有重复。
3. 将新索引记录插入对应位置。
   不需要为了读取这个索引页而发生磁盘 I/O。


此时，如果换成普通索引，流程也很类似：
- 找到内存中的目标索引页。
- 确定插入位置。
- 插入索引记录。
普通索引不需要执行唯一性约束检查，因此会少一部分检查工作。
结论：两者都在 Buffer Pool 时，普通索引的 Change Buffer 优势基本不存在。 但这不代表两者每一步完全相同。
三、情况 2：普通索引页在 Buffer Pool 中
假设 idx_id_card 的目标页已经在内存中。
普通索引：idx_id_card 的目标页已在内存

Buffer Pool
……110101200001011233、110101200001011235……


1. 找到插入位置。
2. 直接修改内存中的索引页。
3. 后续通过 InnoDB 的正常刷脏机制将修改持久化。
   同样不需要为了读取目标页而访问磁盘。


注意，普通索引并不是说“只要能使用 Change Buffer，就一定要使用”。
目标页已经在 Buffer Pool 时，InnoDB 通常直接修改该页，不需要通过 Change Buffer 延迟这次修改。
四、情况 3：唯一索引页不在 Buffer Pool 中
现在假设 uk_id_card 的目标索引页已经被淘汰出 Buffer Pool，当前只能从磁盘读取。
唯一索引：目标页不在内存

磁盘
保存着目标 B+Tree 索引页

为了检查唯一性，需要获取相关索引信息

将目标页读入 Buffer Pool
检查是否存在重复值


插入索引记录，后续再按正常机制刷脏

为什么不能像普通索引那样先把修改记下来，以后再检查？
因为唯一索引必须保证：数据库不能插入重复的索引值。
例如，磁盘中可能已经存在：
110101200001011234 → 用户 A


此时又插入相同的身份证号码。如果数据库不先确认唯一性，就无法安全地接受这次插入。
因此，唯一索引不能像符合条件的普通二级索引那样，依赖 Change Buffer 延迟对目标页的修改。
这里说的是需要读取目标页的逻辑要求，并不意味着一定发生物理磁盘读取：如果目标页被其他线程提前加载进 Buffer Pool，就不需要再次读盘。
五、情况 4：普通索引页不在 Buffer Pool 中
这是文章最想强调的场景。
普通二级索引：目标页不在内存

磁盘
保存着目标 B+Tree 索引页


Change Buffer
记录这次对二级索引的修改，暂时不必读取目标页。

以后读取目标页，或后台执行合并

将积累的修改合并到真正的索引页

举个更直观的例子：假设系统正在批量导入 100 万条历史用户记录，目标索引页大部分都不在 Buffer Pool。
对于符合条件的普通二级索引，InnoDB 可以把多个索引修改暂存在 Change Buffer 中，不必每插入一条记录就立即读取对应的目标页。
这样就有机会减少大量随机读取。
但如果插入后立刻查询同一个索引页，查询可能需要把目标页读入内存，并触发相关修改的合并。此时 Change Buffer 的优势就会缩小。
六、四种情况总结
索引类型	目标页在 Buffer Pool	目标页不在 Buffer Pool
唯一索引	内存中检查唯一性，然后修改索引页	需要获取目标页相关信息以检查唯一性，再修改
普通二级索引	通常直接修改内存中的索引页	符合条件时，可以用 Change Buffer 延迟修改
记住最重要的一句话：
唯一索引与普通索引的关键区别，不是“一个在内存、一个在磁盘”，而是当普通二级索引的目标页不在内存时，它有机会通过 Change Buffer 避免立即读取目标页；唯一索引则必须先满足唯一性检查的要求。

-------------------------------------------------------
场景	                    唯一索引与普通索引的差异
查询一条记录	        通常很小，唯一索引找到记录后可以停止查找
目标页已在 Buffer Pool	普通索引的 Change Buffer 优势很小
目标页不在 Buffer Pool	符合条件的普通二级索引可以利用 Change Buffer，减少立即读取目标页的需要
业务必须保证值唯一	    应优先使用唯一索引，保证正确性
-------------------------------------------------------
change buffer 特指一个数据页
    一个数据页的change buffer 记录的变更越多（也就是这个页面上要更新的次数越多），merge时收益就越大。
    如果一个业务 在写之后由于马上要访问这个数据页，则会立即触发 merge 过程
-------------------------------------------------------
普通索引和唯一索引应该怎么选择。其实，这两类索引在查询能力上是没差别的，
主要考虑的是对更新性能的影响。所以，我建议你尽量选择普通索引。
如果所有的更新后面，都马上伴随着对这个记录的查询，那么你应该关闭 change buffer。
而在其他情况下，change buffer 都能提升更新性能。
-------------------------------------------------------
InnoDB Buffer Pool:
    change_buffer +  Pages
    
change_buffer 跟redo log一样 记录的也是delta
page 里记录的是 从磁盘上读取的具体的内容
-------------------------------------------------------
Reglog 的作用不仅仅是普通的恢复功能，还包括 Change Buffer 的恢复
Change buffer 恢复之后，然后在merge的时候才会真正的去读写磁盘 

Change buffer 的主要作用或者说主要策略是，先不要跟磁盘进行交互，先把操作或者说变更写到内存里



-------------------------------------------------------
Change Buffer 负责延迟修改二级索引页，Redo Log 负责支持崩溃恢复，merge 负责最终把待处理修改应用到目标索引页。三者分工不同，
不需要每次插入都立即 merge，才能保证正常的崩溃恢复能力。
